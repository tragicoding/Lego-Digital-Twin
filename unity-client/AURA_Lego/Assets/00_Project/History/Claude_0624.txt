      ② 밤하늘 지평선 빨강 — 원인 규명 + 라이브 조정

공통 원칙: 저결합·중복 제거·확장성·Mock/Server 동일 동작.


────────────────────────────────────────────────────────────────
[세션 1] 가이드 시작부터 시간 흐름
────────────────────────────────────────────────────────────────

## 요구
  대기(attract)·이름 입력 동안에도 시간이 흐름 → 가이드 시작 시점부터 흐르게.

## 원인
  FastSkyDayNight.Update 가 Start 부터 매 프레임 timeOfDay 증가 → 대기부터 진행.

## 수정 (코드)
  - GameFlowManager: 정적 플래그 `GuideStarted` 추가
      · Awake: false (씬 리로드 시 복귀)
      · BeginGuideScenario(): true ('입장' 클릭 = 가이드 시작, 대기화면 없으면 즉시)
  - FastSkyDayNight: `waitForGuideStart`(기본 ON) — GuideStarted 전이면 UpdateTime() 중단.
      태양 회전·조명은 계속 갱신 → 대기화면은 시작 시각(정오)으로 고정된 하늘.
  - 정적 소스 1회 읽기 패턴(XRModeManager/IsGuideMode와 동일) → 저결합, Mock/Server 동일.

## 결과
  대기·이름입력=정지 / 가이드~자유모드=흐름 / 세션종료(리로드)=재정지. 테스트 완료.


────────────────────────────────────────────────────────────────
[세션 2] 밤하늘 지평선 빨강
────────────────────────────────────────────────────────────────

## 원인 (FastSky = 대기 산란 모델, StylisedSky.mat)
  - 셰이더에 밤(Night) 전용 색 없음 → 해가 지평선 아래로 가면 Evening 색이 밤까지 유지.
  - 지평선 글로우 = Evening 산란: `_EveningColour(1,0.5,0.5)` × `_EveningScatterStrength 12`,
    `_EveningThreshold 1.5`(구간이 넓어 밤까지 번짐). 천정은 별도 어두운 색이라 정상.
  - 주의: `_SkyColour`는 셰이더 미사용(죽은 프로퍼티), FastSky_Sun_Color는 씬에 없음(원인 아님).

## 노브 (라이브 조정)
  - `_EveningThreshold` ↓ : 저녁색을 실제 노을 구간으로 좁힘(밤 빨강 제거, 석양 유지) — 밤 1순위
  - `_EveningScatterStrength` ↓ : 지평선 글로우 강도 ↓
  - `_EveningColour` : 색조 중화

## 처리
  사용자 라이브 조정으로 해결(머티리얼 값 반영). 색 튜닝은 반드시 게임뷰 기준(아래 세션 6).


────────────────────────────────────────────────────────────────
[세션 3] 터널링 비네트 도입·튜닝
────────────────────────────────────────────────────────────────

## 상황
  프로젝트에 비네트 전무. XRI Starter Assets의 TunnelingVignette 프리팹/컨트롤러는 존재.
  리그: DynamicMoveProvider(연속 이동 3m/s) + SnapTurnProvider(스냅 45°, 스무스턴 OFF).

## 셋업
  TunnelingVignette 프리팹을 Main Camera 자식으로 부착 → Controller의
  Locomotion Vignette Providers 에 Provider 연결.

## 튜닝 (피드백 반영)
  - 이동 비네트가 거슬림 → Aperture 0.7→0.85, Feathering 0.2→0.35 (약하게/부드럽게).
  - 스냅턴에도 비네트가 걸려 있어 회전 시 깜빡임·멀미 가중 → 스냅턴 Provider 제거(이동만 유지).

## 중요한 진단
  "고개를 물리적으로 돌릴 때 멀미" = 비네트로 못 고침 = 프레임레이트(저더) 문제.
  → 근본 해결은 보류 중인 성능 작업(mecabricks 저폴리/LOD). 비네트는 이동(벡션)용.


────────────────────────────────────────────────────────────────
[세션 4] 컨트롤러 텔레포트 활성화
────────────────────────────────────────────────────────────────

## 발견
  - 텔레포트 2갈래: (A) 공용 PlayerTeleporter(CC-safe, 가이드/열기구/지도용, 작동 O),
    (B) XRI 컨트롤러 텔레포트 — 리그에 Provider·양손 인터랙터·입력 모두 배선됨.
  - 그러나 씬에 TeleportationArea/Anchor 대상이 0개 → 컨트롤러 텔레포트 사실상 무효
    (조준 아크는 뜨지만 착지 지점 없음). 자유 이동은 연속 스무스뿐이었음.

## 처리 (에디터)
  - 바닥에 TeleportationArea 부착, Interaction Layer = Teleport(인터랙터 bit31과 일치).
  - 레이어 문제: 인터랙터 Raycast Mask = Default+UI+bit31 이라 Ground(물리 레이어 6) 미포함.
    → 권장안 채택: Ground 레이어를 건드리지 않고 양쪽 Teleport Interactor Raycast Mask 에
      Ground(6) 추가(외과적, NavMesh/접지/충돌매트릭스 무영향).
  - 사거리: 레이는 Projectile Curve(LineType 1). 거리 1순위 레버 = m_Velocity(v² 비례).
    10 → 20 으로 상향(양쪽 인터랙터). MaxRaycastDistance(30)는 직선 전용이라 무관.

## 결과
  컨트롤러 텔레포트 정상 동작·사거리 확대 테스트 완료. 즉시 이동(벡션 0)으로 이동 멀미 완화.

[세션 5] VR에서 MapTeleportUI 버튼 위치 깨짐 (근본 수정)
────────────────────────────────────────────────────────────────

## 증상
  VR 모드에서 MapTeleportUI 버튼들이 의도와 다른 위치로 어긋남(데스크톱은 정상).

## 원인
  ModeAdaptiveCanvas(HeadFollowing)가 Overlay→World 변환 시 sizeDelta 를 임의 고정값
  (_worldSize)으로 설정. 이 캔버스는 CanvasScaler=Constant Pixel Size + 버튼 가장자리 앵커라,
  루트 rect 크기가 (화면 크기 → 고정값)으로 바뀌며 가장자리 앵커 버튼이 재배치됨.
  (1차 시도: referenceResolution 매칭 → ScaleWithScreenSize 아니라 폴백, 효과 없음)

## 근본 수정 (코드, ModeAdaptiveCanvas)
  변환 '직전' Overlay 의 실제 rect.size 를 캡처 → 그대로 World sizeDelta 로 사용.
    · rect 크기 불변 → 가장자리 앵커·Constant Pixel Size 무관하게 데스크톱과 동일 보존.
    · 캡처 실패(0) 시에만 referenceResolution/_worldSize 폴백.
  + `_worldWidthMeters`(기본 0) 추가: >0이면 캡처 폭에 맞춰 스케일 자동 산출 →
    화면 해상도와 무관한 일정 물리 크기. 0이면 기존 _scale 사용.
  + (1차) `_matchCanvasScalerResolution`(기본 ON): CanvasScaler ScaleWithScreenSize면
    referenceResolution 을 폴백 크기로 사용.

## 결과
  버튼이 데스크톱과 동일 위치로 복원 확인. 사용자 _worldWidthMeters=0 유지로 확정.
  ※ 모든 HeadFollowing 캔버스에 적용 — 각 캔버스 크기는 _worldWidthMeters/_scale 로 조정 가능.
  ※ 가장자리 앵커는 작성·런타임 종횡비 동일 전제에서 정확(전시 해상도 고정이면 무관).
    근본적으로는 버튼을 중앙 앵커로 두는 것이 가장 안전.
