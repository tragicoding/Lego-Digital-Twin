[세션 3] (진단) MeshCollider Fast Midphase 경고 — 보류
────────────────────────────────────────────────────────────────

## 증상
  "Source mesh has over 2,097,152 triangles ... using the Fast Midphase option.
   ... could be to turn off the Fast Midphase. Source mesh name: TM"
  (씬 로드 시 Internal_RestoreLastOpenedScenes 시점 1회)

## 의미 (에러 아님, 경고)
  이름 "TM" 메시(삼각형 210만 초과)를 MeshCollider 가 Fast Midphase(BVH34)로 쿠킹.
  PhysX 가 이 한계 초과 메시에서 일부 충돌을 놓칠 수 있다는 알려진 제약.
  씬 MeshCollider 123개 전부 기본 m_CookingOptions: 30 (= UseFastMidphase(16) 포함).

## 해결 방향 (택1, 미적용)
  ① (권장) 210만 폴리 메시를 콜라이더로 쓰지 않기 — 저폴리 프록시/Box 콜라이더로 교체.
     이 프로젝트는 이미 Ground 레이어 레이캐스트로 오브제 안착(0613) → 프록시면 충분.
  ② 해당 MeshCollider Cooking Options 에서 Use Fast Midphase 해제(YAML 30→14).
     정확도 우선(BVH33) 전환 → 경고 해소, 충돌 정상. 베이크 약간 느려짐.
  ③ 무시 — 플레이에서 충돌 정상이면 둬도 됨.

## 결정
  사용자가 보류. "TM" 사용 GameObject 가 특정되면 ② 를 Main.unity 에서 콜라이더 1개만
  수정(씬 변경 = 사전 확인). ① 은 에디터 작업이라 절차 안내로 처리.

[세션 4] VR ↔ 키보드+마우스 자동전환 — 런타임 구현
────────────────────────────────────────────────────────────────

## 결정사항 (사용자)
  - 전제 하드웨어: PC 테더드 VR = Meta Quest 3 + Quest Link/Air Link (Windows Standalone 빌드).
    Android(Quest 단독) 빌드는 항상 착용이라 자동전환 무의미 → 대상 아님(기존 Oculus 설정 유지).
  - 전환 시점: 시작/대기화면에서 1회 판정 후 세션 동안 고정(라이브 착탈 전환 아님 — 견고).
  - 작업 분담: 런타임 스크립트는 Claude, ProjectSettings/씬/프리팹은 에디터 단계 안내.

## 시작 상태 (확인)
  - XRGeneralSettingsPerBuildTarget: Standalone=로더 없음·InitOnStart 0(키마),
    Android=Oculus 로더·InitOnStart 1(VR). 빌드 타깃별 단일 모드 고정.
  - EventSystem: InputSystemUIInputModule 사용. activeInputHandler=2(Both).
  - XR 리그: Assets/Prefabs/Object/XR Origin (XR Rig).prefab (XRI 3.2.1 풀 리그, 씬 인스턴스).
  - FreeCameraController.Awake() 가 XR 트래킹/이동 컴포넌트를 "무조건" 비활성화 → VR 공존 불가.
  - 설치 패키지: openxr 1.15.1, xr.interaction.toolkit 3.2.1, xr.management 4.5.1, oculus 4.5.4 등.

## 설계 (저결합·중복 제거·확장성·Mock/Server 동일)
  - 단일 소스 XRModeManager 가 시작 시 1회 모드 판정 → 정적 Mode/Resolved + ModeResolved 이벤트.
  - 매니저는 FreeCamera·EventSystem·XR 리그·SessionManager 를 직접 참조하지 않음.
    각 컴포넌트가 정적 상태를 읽어 "스스로" 구성(새 시스템은 이벤트만 구독하면 확장).
  - 데이터 소스(Mock/Server) 미참조 → 모드는 하드웨어(착용)로만 결정 → 서버 모드 동일 동작(구조적 보장).
  - XR 끄는 로직은 FreeCameraController 한 곳에만 유지하되 "데스크톱 확정 시에만"으로 조건화(중복 0).

## 신규: Scripts/Core/AppMode.cs
  enum { DesktopKBM, VR }. 데이터 소스 무관 — 하드웨어로만 결정.

## 신규: Scripts/Core/XRModeManager.cs (DontDestroyOnLoad 싱글톤)
  - 정적 Mode/Resolved + event ModeResolved. 인스펙터 _override(Auto/ForceVR/ForceDesktop),
    _minSettle(0.5), _settleTimeout(2), _stopXrInDesktop(true).
  - 판정 규칙(Auto):
      · userPresence=true 감지 → 즉시 VR 확정.
      · _minSettle 후에도 활성 HMD 없음(XRSettings.isDeviceActive=false) → 즉시 데스크톱(미연결).
      · HMD 연결됐으나 미착용 → _settleTimeout 까지 착용 대기, 끝나면 데스크톱.
  - IsHmdWorn(): XRSettings.isDeviceActive + InputDevices.GetDeviceAtXRNode(Head)
    + CommonUsages.userPresence (미지원 런타임이면 유효 HMD=착용으로 간주).
  - 데스크톱 확정 시 StopXr(): XRGeneralSettings.Manager.StopSubsystems()+DeinitializeLoader()
    → 평면 렌더링/VR 오버헤드 제거.
  - 씬 리로드(A안 전시 루프)에도 한 번 정해진 모드 유지(Resolved 면 재판정 안 함).
  - ResolveNow(): 외부(대기화면 입장 직전)에서 즉시 확정 강제 옵션.

## 신규: Scripts/Core/EventSystemModeBinder.cs ([RequireComponent(EventSystem)])
  - _vrModules / _desktopModules (Behaviour[]) 로 UI 입력 모듈을 모드별 1회 토글.
    특정 모듈 타입 비의존(저결합). 매니저 없으면 아무것도 안 바꿔 씬 기본 모듈 유지(무회귀).

## 수정: Scripts/Core/FreeCameraController.cs
  - Awake 의 무조건 DisableConflictingXrComponents() 제거.
  - Update: 모드 확정 전 카메라 조작 보류. 데스크톱이면 동작, VR이면 enabled=false(자유카메라 정지).
  - TryResolveMode(): XRModeManager.Resolved 면 적용. 매니저 없거나 늦으면
    modeResolveTimeout(기본 4s) 후 데스크톱으로 폴백 → 현재 키마 흐름 무회귀.
  - ApplyMode(Desktop): DisableConflictingXrComponents() + SyncLookFromTransforms()(기존 Start 역할).
  - Start() 제거(SyncLook 호출을 ApplyMode 로 이관).

## 검증
  IDE 진단(VS Code/OmniSharp): AppMode/XRModeManager/EventSystemModeBinder/

[세션 5] (진단) 에디터 VR 테스트 — 컨트롤러 이동 안 됨
────────────────────────────────────────────────────────────────

## 증상
  에디터 VR(Quest Link) 테스트에서 컨트롤러로 이동이 안 됨.

## 점검 (정적)
  - XRModeManager 씬 배치됨(_override=Auto, _settleTimeout=2, _stopXrInDesktop=1).
  - EventSystemModeBinder 씬 배치됨. FreeCameraController = XR Origin 프리팹 카메라에 존재(enabled).
  - 프리팹 비활성 컴포넌트 4개 = SnapTurn·Gaze 보조뿐(이동 Provider는 활성). 프리팹엔 이동 꺼진 흔적 없음.

## 원인 (사용자 ForceVR 테스트로 확정)
  ForceVR로 바꾸면 이동 정상 + 로그 "[XRModeManager] 실행 모드 확정: VR".
  → 스크립트·리그·이동 배선은 정상. 문제는 Auto 판정이 VR이 아니라 DesktopKBM으로 떨어진 것.
  - Auto는 IsHmdWorn()=userPresence에 의존. 에디터+Link에선 userPresence가 false로 자주 보고됨.
  - _settleTimeout(2초) 안에 착용 미확인 → DesktopKBM 확정 → StopXr() + FreeCameraController가
    ConflictingTypes(ContinuousMove/DynamicMove/GrabMove/Turn Provider…)를 비활성화 → 컨트롤러 이동 불가.
  - 부가 위험: _minSettle(0.5s) 조기 break가 OpenXR 콜드스타트보다 빠르면 빌드에서도 오판 가능.

[세션 6] VR/키마 판정 창을 '대기영상 단계' 전체로 확장 (게이트 연동)
────────────────────────────────────────────────────────────────

## 요구
  대기영상(AttractVideoRoot: 0614_4.mp4) 재생 중, 이름 입력으로 넘어가기 전이면
  언제든 헤드셋 착용이 감지되면 VR로 전환.

## 기존 한계
  판정은 Awake 직후 ~2초 창에서 1회뿐 → 대기영상과 무관하게 이미 고정.
  ResolveNow()는 정의만 있고 호출처 0(grep 확인). WaitingScreenUI는 XRModeManager 미참조.

## 설계 (저결합 — XRModeManager는 대기화면을 모름)
  XRModeManager에 범용 게이트 메서드 2개만 노출, WaitingScreenUI가 null-safe 호출만.
  commit 지점 = 대기영상을 떠나는 순간(AnyPress → AdvanceFromAttract).

## 수정 1: Scripts/Core/XRModeManager.cs
  - 필드 _gated 추가.
  - BeginGatedResolve() 신규: 게이트 열기 — 자동 데스크톱 확정 보류, 착용 시에만 즉시 VR.
  - ResolveRoutine() 재작성: while(true) — 착용은 게이트 무관 즉시 VR. _gated면 _settleTimeout
    자동 확정 스킵(데스크톱은 ResolveNow()로만). 게이트 안 열리면 기존 타임드 동작 100% 동일(무회귀).

## 수정 2: Scripts/UI/WaitingScreenUI.cs (using LegoTwin.Core 추가)
  - Start(): _attractActive면 XRModeManager.Instance?.BeginGatedResolve()
    (Awake 순서 무관하게 Instance 보장. 대기영상 없으면 게이트 안 열어 기본 판정 유지).
  - AdvanceFromAttract(): XRModeManager.Instance?.ResolveNow() = commit(미착용이면 데스크톱).

## 수정 3: Scripts/Core/FreeCameraController.cs
  - TryResolveMode(): XRModeManager.Instance 존재 시 확정까지 무한 대기(게이트 중 스스로
    데스크톱 확정해 이동 Provider 끄는 것 방지). 4초 폴백은 매니저가 아예 없을 때만(무회귀).

## 동작 결과
  대기영상 중 아무 때나 착용 → 즉시 VR. 클릭/키로 이름 입력 진입 순간 미착용이면 데스크톱 확정·고정.
