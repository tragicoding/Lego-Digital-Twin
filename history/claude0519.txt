# Lego-Digital-Twin / MINIVERSE Unity Integration Prompt
# 작성일: 2026-05-19
# 목적: feature/unity 브랜치와 feature/backend 브랜치의 Unity 통합 방향 정리

현재 Lego-Digital-Twin / MINIVERSE 프로젝트에서 Unity 개발 팀원과 백엔드/연동 개발자인 내가 처음으로 Unity 프로젝트를 합치려고 한다.

중요한 상황:
1. 팀원의 GitHub branch:
   https://github.com/tragicoding/Lego-Digital-Twin/tree/feature/unity

2. 내 GitHub branch:
   https://github.com/tragicoding/Lego-Digital-Twin/tree/feature/backend

3. 팀원 브랜치의 Unity 프로젝트는 팀원 로컬에서 정상 실행된다.
4. 내 브랜치에는 FastAPI 서버 연동, 실제 서버 데이터 수신, 캐릭터/오브제 데이터 구조, 네트워크 관련 코드, 캐릭터 애니메이션 접근 함수 등이 포함되어 있거나 포함될 예정이다.
5. 두 브랜치의 Unity 디렉토리 구조와 에셋 배치 구조가 다르다.
6. 따라서 내 Unity 폴더를 팀원의 Unity 프로젝트 위에 그대로 덮어쓰면 안 된다.
7. Unity 통합 기준은 팀원의 feature/unity 브랜치로 둔다.
8. 내 브랜치의 Unity 관련 코드는 필요한 부분만 모듈 형태로 이식한다.

가장 중요한 원칙:
- 팀원은 서버 없이도 자신의 로컬 Unity 프로젝트에서 개발할 수 있어야 한다.
- 팀원은 Mock Data를 사용해서 캐릭터 등장 위치, 이동 경로, 튜토리얼 시나리오, 말풍선 연출, 오브제 배치 등을 개발한다.
- 나는 Mock Data가 아니라 실제 FastAPI 서버에서 전달되는 데이터를 사용해서 통합 테스트와 서버 연동을 진행한다.
- 즉, Unity 코드에는 반드시 Mock Mode와 Server Mode가 분리되어 있어야 한다.

구분:
1. Mock Mode
   - 팀원이 로컬에서 서버 없이 개발할 때 사용
   - Resources 또는 StreamingAssets에 있는 mock_session.json을 읽음
   - 기본 캐릭터/오브제 prefab 또는 fallback model을 사용
   - 서버, WebSocket, FastAPI가 없어도 Unity 씬이 실행되어야 함
   - 팀원은 이 모드로 NPC 이동, 말풍선, 시나리오, 위치 배치 작업을 진행

2. Server Mode
   - 내가 실제 FastAPI 서버와 연동할 때 사용
   - FastAPI에서 /unity/sessions/{session_id} 또는 WebSocket session_ready 이벤트로 데이터를 받음
   - 실제 Tripo API 결과로 생성된 character/object model_url을 사용
   - DownloadManager 또는 RuntimeModelImporter를 통해 실제 모델을 로드
   - 실제 character_npc_name, object_name, bubble_text 등을 사용
   - 최종 전시 통합 테스트에서 사용

따라서 Unity 쪽에는 다음과 같은 모드 전환 구조가 필요하다.

예상 구조:
public enum DataSourceMode
{
    Mock,
    Server
}

public class SessionManager : MonoBehaviour
{
    public DataSourceMode dataSourceMode = DataSourceMode.Mock;

    // Mock Mode일 때는 mock_session.json 사용
    // Server Mode일 때는 FastAPI 서버에서 실제 session 데이터 사용
}

팀원이 Unity 프로젝트를 열었을 때 알아야 할 점:
- 기본값은 Mock Mode로 설정한다.
- 팀원은 서버를 켜지 않아도 mock_session.json을 기준으로 개발할 수 있다.
- mock_session.json은 실제 서버 응답과 최대한 같은 구조로 만든다.
- 나중에 서버와 합칠 때는 DataSourceMode를 Server로 바꾸면 실제 서버 데이터를 사용하도록 설계한다.
- Mock 데이터 구조와 실제 서버 데이터 구조는 동일하거나 거의 동일해야 한다.
- 그래야 Mock Mode에서 만든 캐릭터 이동/말풍선/시나리오 코드가 Server Mode에서도 그대로 동작한다.

이번 전시 기획 최신 버전:
- 기존 집, 자동차, 건축물 흐름은 제거한다.
- 3D로 전환되는 대상은 오직 두 가지다.
  1. character
  2. object
- character는 3D 변환 + 애니메이션 적용 대상이다.
- object는 3D 변환만 수행하는 정적 오브제다.

Unity에서 사용할 핵심 데이터:
- session_id
- character_npc_name
- object_name
- bubble_text, 필요 시
- character asset
- object asset
- character animations metadata

캐릭터 애니메이션 접근 방식:
Unity 개발자가 나중에 게임 시나리오를 만들 때 함수로 쉽게 접근할 수 있어야 한다.

CharacterAnimationController.cs에는 최소한 다음 함수가 있어야 한다.

public class CharacterAnimationController : MonoBehaviour
{
    public void animation_walk()
    {
        PlayAnimation("walk");
    }

    public void animation_Hello()
    {
        PlayAnimation("hello");
    }

    public void PlayAnimation(string animationKey)
    {
        // Animator trigger 또는 clip 실행
    }
}

팀원은 이후 다음처럼 사용할 수 있어야 한다.
- npc.Animation.animation_walk();
- npc.Animation.animation_Hello();
- npc.Animation.PlayAnimation("walk");
- npc.Animation.PlayAnimation("hello");

GuideNPCController.cs에는 Unity 개발자가 시나리오를 붙이기 쉬운 함수가 필요하다.

예상 함수:
public class GuideNPCController : MonoBehaviour
{
    public void SetNpcName(string name);
    public void SetBubbleText(string text);
    public void MoveTo(Vector3 targetPosition);
    public void StartGuideScenario();
}

팀원은 Mock Mode에서 다음 작업을 진행할 수 있어야 한다.
1. 캐릭터가 어디서 등장할지 결정
2. 캐릭터가 어디로 이동할지 결정
3. 캐릭터가 오브제가 있는 곳까지 안내하는 시나리오 작성
4. 캐릭터 말풍선 출력 타이밍 작성
5. animation_walk(), animation_Hello() 호출 타이밍 작성
6. 오브제 배치 위치 결정

나는 Server Mode에서 다음 작업을 진행한다.
1. FastAPI 서버에서 실제 session 데이터 수신
2. 실제 character/object model_url 수신
3. 실제 캐릭터 이름과 오브제 이름 수신
4. 실제 모델 다운로드 및 로딩
5. Mock Mode에서 만든 시나리오가 실제 서버 데이터에서도 작동하는지 확인

Unity 디렉토리 통합 원칙:
- feature/unity의 Unity 프로젝트를 기준으로 유지한다.
- Scenes, ProjectSettings, Packages, External Assets는 무작정 덮어쓰지 않는다.
- feature/backend의 Unity 폴더 전체를 merge하지 않는다.
- 필요한 C# 코드만 Assets/00_Project/Scripts 아래로 모듈 형태로 이식한다.
- .meta 파일 참조가 깨지지 않도록 Unity Editor에서 이동하는 것을 우선한다.

Mock Mode와 Server Mode의 흐름:

Mock Mode:
1. SessionManager가 dataSourceMode == Mock인지 확인
2. MockSessionLoader가 Resources/Mock/mock_session.json 로드
3. AssetSpawnManager가 mock character/object 데이터를 기반으로 prefab 생성
4. GuideNPCController에 character_npc_name과 bubble_text 전달
5. CharacterAnimationController로 walk/hello 함수 테스트 가능
6. 팀원은 이 상태에서 시나리오 개발

Server Mode:
1. SessionManager가 dataSourceMode == Server인지 확인
2. ApiClient가 FastAPI 서버에서 /unity/sessions/{session_id} 호출
3. 실제 character/object model_url 수신
4. DownloadManager 또는 RuntimeModelImporter가 모델 다운로드 및 로드
5. AssetSpawnManager가 실제 character/object 생성
6. Mock Mode에서 만든 GuideNPCController와 CharacterAnimationController 흐름 그대로 사용

중요:
Mock 데이터와 실제 서버 데이터의 JSON 구조는 최대한 동일해야 한다.
따라서 코드에서 Mock 전용 필드와 Server 전용 필드가 갈라지지 않도록 주의한다.
MockSessionLoader와 ApiClient는 둘 다 SessionData를 반환하도록 설계한다.

예상 인터페이스:
public interface ISessionDataProvider
{
    Task<SessionData> LoadSessionDataAsync(string sessionId = null);
}

구현체:
- MockSessionDataProvider
- ServerSessionDataProvider

SessionManager는 현재 모드에 따라 provider를 선택한다.

작업 요청:
1. 현재 feature/unity와 feature/backend의 Unity 구조를 비교해줘.
2. feature/unity를 기준으로 통합 계획을 세워줘.
3. feature/backend에서 가져와야 할 코드만 식별해줘.
4. 서버 없이 팀원이 개발 가능한 Mock Mode를 먼저 설계해줘.
5. 실제 서버 데이터로 동작할 Server Mode도 함께 설계해줘.
6. MockSessionLoader와 mock_session.json을 만들어줘.
7. SessionData / AssetData / AnimationData 클래스를 만들어줘.
8. CharacterAnimationController skeleton을 만들어줘.
9. GuideNPCController skeleton을 만들어줘.
10. SessionManager에서 Mock/Server 모드를 전환할 수 있게 해줘.
11. 기존 feature/unity 씬과 에셋 참조가 깨지지 않도록 주의해줘.
12. 변경 전 통합 계획을 먼저 설명하고, 내가 승인하면 실제 파일 수정에 들어가줘.

절대 하지 말 것:
- feature/backend의 Unity 폴더를 feature/unity 위에 통째로 덮어쓰기
- Scenes, ProjectSettings, Packages를 임의로 덮어쓰기
- 팀원 에셋 디렉토리 구조를 무리하게 변경하기
- 서버가 없으면 Unity가 실행되지 않는 구조로 만들기
- Mock 데이터와 실제 서버 데이터 구조를 다르게 만들어 나중에 통합이 어려워지게 하기

최종 목표:
1. 팀원은 Mock Mode로 서버 없이 Unity 시나리오 개발 가능
2. 나는 Server Mode로 실제 FastAPI 서버 데이터를 사용해 통합 테스트 가능
3. 두 모드는 같은 SessionData 구조를 사용
4. 캐릭터 애니메이션은 animation_walk(), animation_Hello()로 접근 가능
5. 나중에 Mock Mode에서 만든 캐릭터 이동/말풍선/시나리오 로직이 실제 서버 데이터에서도 그대로 동작
6. feature/unity 브랜치의 정상 실행 상태를 유지하면서 필요한 연동 모듈만 안전하게 추가

먼저 이 문서를 읽고, 현재 feature/unity와 feature/backend의 Unity 구조를 비교한 뒤, 실제 수정 전에 통합 계획과 파일 이동/추가 목록을 먼저 제안해줘. 내가 승인하기 전에는 파일을 수정하지 마.
