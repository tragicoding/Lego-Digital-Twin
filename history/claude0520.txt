1. 프로젝트 개요
--------------------------------------------------

Lego-Digital-Twin / MINIVERSE 프로젝트 소개를 작성한다.

내용:
- 관객이 현실에서 조립한 레고 캐릭터와 오브제를 촬영한다.
- 촬영된 이미지는 3D 모델로 변환된다.
- 캐릭터는 애니메이션이 적용되어 Unity VR 월드에서 NPC로 등장한다.
- 오브제는 정적 3D 모델로 Unity VR 월드에 배치된다.
- 현재 전시 버전의 3D 전환 대상은 character와 object 두 가지다.

정리:
- character: 3D 변환 + 애니메이션 적용
- object: 3D 변환만 수행

7. Unity Developer Git 전략
--------------------------------------------------

Unity developer는 다음 방식으로 작업한다.

1. develop에서 최신 내용 pull
2. feature/unity 브랜치로 이동

- Unity 실행은 반드시 Windows에서 한다.

--------------------------------------------------
8. Backend / Frontend / System Developer Git 전략
--------------------------------------------------

Backend / Frontend / System developer는 다음 방식으로 작업한다.

1. develop에서 최신 내용 pull
2. 작업 성격에 맞는 브랜치로 이동
3. 작업 후 각자의 브랜치에 commit / push
4. develop으로 Pull Request 생성
5. 리뷰 후 develop에 merge

브랜치 정책:
- 새로운 프레임워크 실험 또는 바뀐 기획 검증: test_app 또는 feature/test-app
- Frontend 개발: frontend 또는 feature/frontend
- Backend 개발: backend 또는 feature/backend
- System 자동화: system 또는 feature/system
- Unity 개발: feature/unity

현업 스타일에 맞춰 다음 원칙을 반영한다.
- develop은 통합 브랜치다.
- main 또는 master는 최종 안정 버전 또는 배포 버전으로 사용한다.
- 직접 develop에 push하지 않는다.
- 모든 기능 작업은 기능 브랜치에서 진행한다.
- Pull Request 기반으로 develop에 병합한다.
- 작업 전 항상 develop 최신 내용을 pull한다.
- 충돌 발생 시 담당자와 확인 후 해결한다.

이미 저장소에 frontend, backend, system, test_app과 같은 기존 브랜치명이 사용 중이면 기존 브랜치명을 존중하되, README에서 명확히 정리한다.

9. 협업 원칙
--------------------------------------------------

다음 내용을 README에 추가한다.

- develop은 통합 브랜치다.
- main/master는 최종 안정 버전 또는 배포 버전으로만 사용한다.
- 직접 develop에 push하지 않는다.
- 모든 기능 작업은 feature 또는 역할별 브랜치에서 진행한다.
- 작업 전 develop 최신 내용을 pull한다.
- 충돌이 발생하면 관련 담당자와 확인 후 해결한다.

- .env.example은 커밋한다.
- 대용량 모델/생성 결과물은 필요 시 Git LFS 또는 별도 storage 정책을 따른다.

[3] 최상위 git.md 작성
==================================================

최상위 디렉토리에 git.md를 작성한다.

목표:
팀원의 AI Agent가 “git.md를 읽고 git 작업해”라는 명령을 받았을 때, 자동으로 안전한 Git 작업 방식을 따를 수 있어야 한다.

git.md는 명령형 규칙으로 작성한다.

--------------------------------------------------
1. 기본 원칙
--------------------------------------------------

- 직접 develop에 commit하지 않는다.
- 반드시 역할별 브랜치 또는 feature 브랜치에서 작업한다.
- 작업 전 현재 브랜치와 변경사항을 확인한다.
- 변경사항이 있으면 사용자 확인 없이 checkout/merge/rebase 하지 않는다.
- PR 대상은 develop이다.
- main/master는 직접 작업하지 않는다.
- 사용자의 승인 없이 commit/push 하지 않는다.

--------------------------------------------------
2. 브랜치 정책
--------------------------------------------------

- develop: 통합 브랜치
- feature/unity: Unity 개발
- frontend 또는 feature/frontend: Frontend 개발
- backend 또는 feature/backend: Backend 개발
- system 또는 feature/system: System 자동화
- test_app 또는 feature/test-app: 새로운 프레임워크, 실험성 기능, 바뀐 기획 검증

기존 저장소에 이미 사용 중인 브랜치명이 있다면 현재 브랜치 목록을 확인하고 그 규칙에 맞춰 사용한다.

--------------------------------------------------
3. 작업 시작 절차
--------------------------------------------------

공통:
git status
git branch
git fetch origin
git checkout develop
git pull origin develop

작업 유형별:
Unity:
git checkout feature/unity
git pull origin feature/unity

Backend:
git checkout backend
또는
git checkout feature/backend

Frontend:
git checkout frontend
또는
git checkout feature/frontend

System:

또는

Test App:

git checkout feature/test-app

브랜치가 없으면 사용자에게 생성 여부를 먼저 물어본다.

--------------------------------------------------
4. 작업 중 규칙
--------------------------------------------------

- 작은 단위로 commit한다.
- 기능 단위로 commit한다.
- 커밋 전 테스트 가능한 범위에서 테스트한다.
- README/문서 변경이 필요한 구조 변경이면 문서도 함께 수정한다.
- Unity 파일 이동 시 .meta 파일 보존 필수
- 불필요한 대용량 파일 커밋 금지
- .env 파일 커밋 금지
- Library, Temp, obj, Logs 커밋 금지

--------------------------------------------------
5. 커밋 전 체크리스트
--------------------------------------------------

- git status 확인
- 변경 파일 목록 확인
- 의도하지 않은 파일 포함 여부 확인
- .env 포함 여부 확인
- Unity Library/Temp/obj/Logs 포함 여부 확인
- 필요한 README 업데이트 여부 확인
- 테스트 여부 확인

--------------------------------------------------
3. Git 작업 원칙
--------------------------------------------------

- git.md를 따른다.
- 작업 전 git status 확인
- commit 전 사용자에게 반드시 확인
- push 전 사용자에게 반드시 확인
- PR 생성 전 사용자에게 반드시 확인
- 사용자의 명시적 승인 없이 commit/push 하지 않는다.
- 사용자의 명시적 승인 없이 merge/rebase 하지 않는다.

--------------------------------------------------
4. Unity 작업 원칙
--------------------------------------------------

- Unity는 Windows에서 실행한다.
- Unity 개발자는 feature/unity 브랜치를 사용한다.
- Unity 관련 파일 이동은 .meta 파일에 주의한다.
- Library, Temp, obj, Logs는 커밋하지 않는다.
- Mock Mode와 Server Mode를 분리한다.
- 팀원은 Mock Mode로 개발 가능해야 한다.
- 실제 서버 연동은 Server Mode에서 처리한다.

--------------------------------------------------
5. Backend / Frontend 작업 원칙
--------------------------------------------------

- Linux 또는 WSL/Linux 기준으로 개발한다.
- backend는 FastAPI, Redis/RQ Worker, PostgreSQL, Tripo API 연동 중심이다.
- frontend는 태블릿 UI, 촬영, 이름 입력, 로딩 UI 중심이다.
- Docker / requirements / package.json 변경 시 README도 함께 수정한다.

--------------------------------------------------
6. Trouble Shooting 기록 원칙
--------------------------------------------------

문제 해결 경험이 생길 때마다 Claude는 history 폴더에 Trouble Shooting 문서를 작성해야 한다.

규칙:
- 저장 위치: history/
- 파일명 형식: Trouble_Shooting00.txt, Trouble_Shooting01.txt, Trouble_Shooting02.txt ...
- 기존 파일 번호를 확인하고 다음 번호로 생성한다.
- 이미 존재하는 파일을 덮어쓰지 않는다.

Trouble Shooting 문서에 포함할 내용:
1. 발생 일자
2. 발생 환경
3. 문제 상황
4. 에러 메시지
5. 원인 분석
6. 해결 방법
7. 재발 방지 방법
8. 관련 파일/명령어
9. 참고 사항

예시 파일:
history/Trouble_Shooting00.txt

예시 내용:
# Trouble Shooting 00

## Date
YYYY-MM-DD

## Environment
- OS:
- Branch:
- Module:
- Tool:

## Problem
문제 상황 설명

## Error Message
에러 메시지

## Cause
원인 분석

## Solution
해결 방법

## Prevention
재발 방지 방법

## Related Files / Commands
관련 파일 및 명령어

## Notes
추가 참고 사항

==================================================
[5] 개발환경 작성
==================================================

README와 하위 README에 개발환경을 명시한다.

필수 구분:
1. Backend / Frontend
   - Linux 또는 WSL/Linux
   - Docker / Docker Compose
   - Python
   - FastAPI
   - PostgreSQL
   - Redis
   - RQ Worker
   - Node.js
   - React / Vite / TypeScript / Tailwind CSS

2. Unity
   - Windows
   - Unity Hub
   - Unity Editor
   - Unity 실행은 반드시 Windows

3. Git / Collaboration
   - GitHub
   - develop branch
   - feature branches
   - Pull Request workflow

실제 버전은 프로젝트 파일 또는 현재 환경에서 확인 가능한 경우에만 작성한다.
확실하지 않으면 TODO로 표시한다.

==================================================
[6] 작업 방식
==================================================

작업 순서:
1. 현재 프로젝트의 실제 디렉토리 구조 확인
2. 기존 README.md와 하위 README.md 존재 여부 확인
3. 최상위 README.md 수정
4. apps/backend/frontend/unity-client README.md 수정 또는 생성
5. 최상위 git.md 생성
6. 최상위 CLAUDE.md 생성 또는 수정
7. history 폴더 존재 여부 확인
8. Trouble Shooting 문서 규칙을 CLAUDE.md에 반영
9. 변경 파일 목록 요약
10. commit하지 말고 사용자에게 확인 요청

주의:
- 실제 파일 구조를 보지 않고 임의 구조를 단정하지 말 것
- 명령어가 확실하지 않으면 TODO로 표시
- 문서 수정 작업이므로 코드 기능 구현은 하지 말 것
- 이번 작업에서 commit/push는 하지 말 것
- 문서 수정 후 사용자에게 확인 요청할 것

위 요구사항을 기준으로 먼저 현재 디렉토리 구조와 기존 README 파일들을 확인한 뒤, 문서 수정 계획을 요약해줘. 그 다음 README.md, 하위 README.md, git.md, CLAUDE.md를 수정해줘. 수정이 끝나면 commit하지 말고 변경 파일 목록과 검토 방법을 보고해줘.
